# Campaign 1 operating checkpoint

This controlled production campaign selects 30 resolved entities, using existing target-field gaps and regional/historical value. Research only capital, leadership, political/institutional and currency. The selection contains 2,356 category/year opportunities, condensed into 30 bounded entity/period assignments, not a global dispatch. Selection dates are research bounds, never evidence of continuous facts.

## Entity assignments

`scripts/research-campaign.mjs init` creates deterministic `core-state` jobs with explicit `categories`, existing facts, sources, mapping/transition cautions and production fingerprints. Initialisation refuses to overwrite a queue. An `entity-core` worker may return individually sourced interval claims in the four declared categories. Ordinary single-specialist jobs retain their restrictions. Omit unsupported fields, record absence, and leave disputed claims in review. Statistics and figures are outside this campaign.

Workers edit only isolated packages and evidence ledgers. The coordinator owns queue transitions, source-body review, acceptance and production integration. Reuse source IDs where the body genuinely supports the claim. Clip evidence to a coherent entity/assignment interval without increasing date precision. Never infer continuity from names, geometry, SUBJECTO or PARTOF.

## Serial context revisions

The original worker package on disk remains immutable. An accepted receipt is valid only for its exact production fingerprint. After each earlier serial integration changes production, the coordinator may explicitly `recontextualize` a retained job, supplying its expected package hash, fresh verified context and a reason. This archives its original package, validation and receipt in `contextRevisions`; changes only the fingerprint; removes acceptance; and returns it to `submitted`.

Revalidation and fresh independent historical acceptance are mandatory. Inspect current mappings, existence bounds, source definitions, old/new facts and every review issue. If intervening changes conflict, hold the package. A context revision never changes claims/evidence or automatically rebases historical meaning. Do not loosen the integrator's fingerprint guard. Record completed integration receipts in the queue before overwriting the completed journal with the next integration. A crash between apply and queue completion must be reconciled from that journal before continuing.

## Checkpoints and recovery

Integrate approximately six entities per checkpoint, serially. Run automated tests and targeted browser checks for changed facts, citation targets, boundary years and requested-year authority; regenerate completeness reports; commit and push; verify clean synchronized main. Run the full historical browser regression once at the campaign end because shared runtime remains unchanged. Keep original Stage 1 packages as historical evidence rather than accepting their stale receipts against changed production.

Resume from queue status and integration receipts, not a chat summary. Retain original packages and source-body evidence. Recover interrupted owners only with documented interruption. No modern fallback, guessed precision, unresolved sovereignty resolution, UI/runtime redesign, version bump or Campaign 2 dispatch is authorised.
